# Migrations and recovery

Migrations are hand-written SQL applied by D1 in lexical order; deploy only backward-compatible changes. `drizzle-kit` is intentionally not part of the toolchain — `packages/db/src/schema.ts` exists so better-auth's Drizzle adapter can read and write the auth tables at runtime, and the SQL files are the source of truth for the schema. Test on a copy, take a D1 export and record R2 object inventory before production changes. Roll forward is preferred; rollback SQL must not discard newly written columns.

The seed is deterministic and for local use only (`packages/db/src/migrations.test.ts` verifies it applies cleanly after every migration, and that the FTS triggers stay in sync through re-indexing, purging, and cascade deletes). Production restore order is D1 schema/data, R2 object validation, FTS rebuild (`INSERT INTO chunk_fts(content,heading,chunk_id,organization_id,version_id) SELECT content,heading,id,organization_id,version_id FROM chunk` after `DELETE FROM chunk_fts`), then Vectorize reindex from chunks. Run tenant-count and citation referential checks before reopening traffic.
